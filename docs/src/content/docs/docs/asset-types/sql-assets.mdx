A SQL asset is a query that produces one table or view. You write the
`SELECT`; Renart handles where the result lands, when it runs, and how it
connects to the rest of the pipeline.

## Create one

On the canvas, add an asset and choose **SQL**. Name it
`<folder>.<name>` — for example `staging.orders` — and that name is how
downstream queries reference it.

## Write the query

The editor knows your pipeline: completions offer upstream tables and
their columns with types, unresolved references are flagged as you type,
and **Format SQL** keeps the style consistent. A typical asset is just a
query:

```sql
SELECT
    o.order_id,
    o.customer_id,
    c.customer_name,
    o.order_date,
    o.status,
    o.total_amount
FROM raw.orders o
JOIN raw.customers c USING (customer_id)
WHERE o.status != 'refunded'
```

Referencing `raw.orders` in `FROM` or `JOIN` is all it takes to depend on
it — Renart infers the dependency and draws the edge on the canvas.
Unqualified names resolve to the matching asset when it's unambiguous. For
relationships the SQL can't express, add a manual dependency in the
workbench's **Dependencies** card.

The editor can also complete tables positively observed on the selected
warehouse. Using one is allowed but highlighted as an external-relation
warning. Choose **Import source asset** from the warning or Type check to review
the exact table name, connection, path, and columns before adding it to the
project.

## Metadata in the workbench

Everything about the asset that isn't the query lives in the workbench
cards next to the editor:

- **Identity** — name, owner, description, tags.
- **Materialization** — whether the asset writes a view, replaces a table
  each run, or updates incrementally.
- **Columns** — names, types, descriptions, and quality checks such as
  `not_null` or `unique`; use **Sync schema** after the SQL changes to compare
  the query, saved declaration, and optional current table.

## Materialization lifecycle

When an incremental table does not exist yet and the selected warehouse can
prove that absence, Renart bootstraps it with the corresponding full-refresh
materialization before continuing. If the target exists as a view while the
asset now declares a table, or the other way around, an ordinary run stops with
a clear blocker. Review a **Full refresh** to replace the observed object kind
on supported warehouses. When the warehouse cannot be inspected confidently,
Renart warns and preserves the configured strategy instead of guessing.

## Check it before it runs

**Inspect** previews the query's result without writing anything. The
**Type check** tab verifies that the declared columns match what the query
actually produces — the same check `renart type-check` runs in CI.
