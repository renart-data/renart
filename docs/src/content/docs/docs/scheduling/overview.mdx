Renart schedules pipelines itself — there is no separate orchestrator to
deploy and babysit. One schedule exists per pipeline and environment, and
scheduled runs execute the pipeline's **deployed snapshot**, not whatever
happens to be in your working tree.

## How deployments, schedules, and runs fit together

Think of the flow as three separate decisions:

1. **Deploy** captures the pipeline's saved files as an immutable snapshot. It
   reviews representative operations, but it does not execute the pipeline.
2. **Schedule** defines when one environment should run and pins that
   environment to one deployment.
3. **Run** is one execution of that pinned deployment for a specific time
   window. Its events and output appear in **Runs**.

| Action | Source used | What changes |
| --- | --- | --- |
| **Review run** in the workspace | Current saved working tree | Starts one manual run; no deployment or schedule pin changes |
| **Review deployment** | Current saved working tree | Creates or reuses an immutable deployment; executes no data |
| **Update schedules** after deployment | The deployment you just reviewed | Moves only the schedule pins you select |
| **Run pinned** on a schedule | That schedule's current deployment | Starts one run without changing the pin |

This separation lets you keep editing after a deployment without silently
changing scheduled behavior. A newer deployment also does not move every
environment automatically: after deploying, select exactly which schedules
should adopt it.

## Create a schedule

In **Schedules**, click **New schedule** and pick:

- the **pipeline** and the **environment** to run against;
- a **cron** expression and **timezone** (for example `0 7 * * 1-5` in
  `Europe/Berlin`);
- a **catch-up policy** — skip missed intervals, or run once to catch up
  after downtime.

Creating a schedule for an environment without a deployed snapshot offers
to **deploy the working tree now and pin this schedule to it**.

Renart writes the desired cadence and environment settings to
`.renart/schedules.yml`, so schedule changes are ordinary reviewable Git diffs.
The exact deployment pin and run history stay local to each machine. On a new
checkout, a declared schedule remains paused until that machine has an explicit
deployment pin.

Optional variable overrides can be stored directly in the declaration. For a
secret value, store an `env:NAME` reference instead; Renart resolves it from the
server process only while validating, planning, or running and does not write
the resolved value to schedule or run state.

:::caution[Use an unattended credential source]
The encrypted local vault locks whenever Renart restarts, so it is not a
durable source of trust for unattended schedules. Bind scheduled connection
credentials to environment variables injected by your service manager,
container runtime, or CI system. See
[Manage connection credentials](/docs/connections-environments/managing-credentials/).
:::

## Deployments keep schedules stable

Deploying records a snapshot of the pipeline as it is; the schedule runs
that snapshot until you redeploy. You can keep editing — and even break —
the working tree without affecting tonight's run. When you're ready, review a
new deployment and explicitly select which schedule pins should advance (or
create the deployment with [`renart deploy`](/docs/reference/cli/) from CI).

## Managing schedules

Each row in the Schedules view shows the cadence, the last success, and a
timeline of recent and upcoming runs. From the row you can pause the
schedule with the toggle, run its exact pin now, review a newer deployment, or
archive it. Removing its declaration keeps local run history and the previous
pin during the configured schedule-history window, so re-adding the same
pipeline/environment key can restore it.
Scheduled runs land in [Runs & history](/docs/workspace/runs-and-history/)
like any other run.

The scheduler runs inside `renart web`. For an always-on machine, the same
scheduler is available headless — see the
[CLI reference](/docs/reference/cli/).
