Notebooks are where analysis starts before it deserves a permanent place in a
pipeline. Every notebook is a folder in your repository, with ordered SQL,
Python, data-source, text, and visualization blocks. Renart executes the
dataflow and keeps its integration tables in one local DuckDB file, so the
notebook can combine unlike sources without creating scratch tables in your
remote warehouses.

## Add data from several systems

Choose **Add data** to create an explicit source block:

- browse a configured warehouse connection and start from a generated
  read-only query;
- select a local file or an object from configured S3-compatible or Google
  Cloud Storage credentials;
- describe an HTTP request and the response records to extract.

A warehouse query runs in that connection's native SQL dialect. Renart copies
the typed result into the notebook's local DuckDB, where downstream SQL and
Python cells can join it with snapshots from other connections. Source cards
show the connection, environment, snapshot age, rows, bytes, and whether the
snapshot is complete or intentionally sampled.

Choose **Full** when downstream work needs the complete result. Choose
**Sample** with an explicit row limit for exploratory work. Preview limits only
control the rows rendered in the browser; Renart does not silently publish a
truncated preview as a complete source table.

## SQL and Python cells

Connectionless SQL cells are local DuckDB transforms. They can refer to other
notebook cells by their concise visible names, and Monaco provides DAG-aware
completion and diagnostics. A SQL source cell instead uses its selected
connection's catalog, dialect, and remote-table completion.

Python cells use the same `materialize()` contract as Python pipeline assets.
They query the notebook's live local session through Renart's built-in SDK:

```python
from renart import query


def materialize():
    orders = query("select * from daily_orders")
    return orders
```

Use **Dependencies** to add third-party packages. The built-in runtime includes
pandas and PyArrow. Python receives query results but never the DuckDB path or
warehouse credentials, and it runs only when you request it; editing Python
does not trigger automatic execution.

Run one cell, run from a cell downward, or **Run all**. Renart keeps successful
result schemas, row counts, source provenance, and definition staleness in the
notebook session so they survive a server restart. Completed relations can be
downloaded as CSV or Parquet.

## Parameters

Choose **Parameters** to add typed notebook inputs. A parameter's ID, type,
default, and optional choices are saved in `notebook.yml`; the value you are
currently exploring stays local to your Renart session. This keeps useful
defaults reviewable in Git without turning every interactive selection into a
file change.

Use the safe `parameter` namespace in SQL:

```sql
select *
from daily_orders
where region = {{ parameter.region }}
  and order_total >= {{ parameter.minimum }}
```

Renart quotes and escapes these values as typed SQL literals, and Monaco offers
the declared IDs inside Jinja expressions. In Python, read the same typed
values from `context.vars`:

```python
from renart import context, query


def materialize():
    region = context.vars["region"]
    orders = query("select * from daily_orders").to_pandas()
    return orders.loc[orders["region"] == region]
```

For file/object paths and HTTP request templates, use
`{{ parameters.region }}`. Exact placeholders in HTTP JSON bodies preserve
boolean, numeric, and list types. Changing a value marks affected notebook
results stale; the runtime value is also part of result fingerprints, so an
export cannot accidentally reuse output produced with another selection.

## Visualizations

Add a **Visualization** block and choose its source result. The visual builder
supports tables, KPIs, bar, line, area, scatter, pie, and donut charts. Use the
**Visual / Definition** switch to edit the same versioned definition through
controls or YAML; switching views does not rewrite the source SQL.

Renart checks referenced fields and compatible field types in the backend. A
renamed or removed result column therefore becomes a targeted visualization
diagnostic while the saved definition remains editable. Multiple
visualizations can read the same cell.

Older notebooks with an `@viz` SQL comment continue to render. Use the
migration action to replace a legacy directive with a durable visualization
block; new visualization edits do not write `@viz` comments.

## Promote a cell to the pipeline

When a transform or source earns a permanent place, open its actions menu and
choose **Promote to pipeline**. Before anything changes, Renart shows the target
pipeline, asset type, source and target connections, materialization, files to
change, and any dialect consequences.

Local SQL and Python become ordinary pipeline assets. A full local-file source
becomes a Seed asset where the target supports one, object-storage sources
become Load assets, and HTTP sources become API assets while retaining the
request and response settings. Connection-bound SQL keeps its source
connection. An intentionally sampled source cannot be promoted until you
change it to **Full**.

Applying the reviewed plan creates the pipeline files, rewrites remaining
notebook references, and removes the promoted blocks as one recoverable
workspace change. If the notebook changed after review, Renart keeps both the
notebook and pipeline untouched and asks you to review again.

## Files like everything else

`notebook.yml` owns block order and durable block IDs. SQL and Python remain
ordinary Bruin asset files, while non-SQL source definitions use small YAML
files beside them. The complete authored state is versioned, diffable, and
protected by a notebook-wide revision when Renart applies a compound change.
