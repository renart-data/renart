# Data Browser → notebook authoring

Status: proposed, 10 September 2026. Plan only.

## Experience

Dragging a table or supported file into a notebook reveals its existing insertion
points between blocks. A drop opens a compact source review; confirmation creates
one source block at that position. Nothing is queried, transferred or run until
the user explicitly runs it. The Data Browser stays open and the notebook keeps
its draft, selection and scroll position apart from revealing the new block.

The same flow must be available through **Add to notebook** on a browser item,
then an insertion-point button. This is the keyboard/mobile equivalent, not a
second implementation or a requirement to perform an unreliable touch drag.

| Browser item | Notebook definition |
| --- | --- |
| Warehouse relation | Connection-bound, read-only SQL source, with server-quoted full catalog/schema/table identity |
| Project file | Existing local file source, project-relative path |
| S3-compatible/GCS object | Existing object-storage source using the configured connection |
| Storage prefix | Review a supported file format and literal prefix/pattern before creating a source; no implicit whole-bucket import |
| Connection alone | Show a source picker; never create an export/destination or infer a table |

Advertise only capabilities the notebook transfer layer actually supports. SFTP
is currently browsable but is not an established notebook source contract: keep
it disabled with an explanation until a typed, bounded transfer implementation
and tests land. GCS notebook sources already exist, independently of Data Browser
provider coverage. Unsupported formats remain browsable but are not importable.

## Architecture

1. Generalize `DataBrowserTransfer`'s pipeline-only destination into a tagged
   destination: pipeline ID or notebook ID. Keep the same-window nonce-only MIME,
   project/environment checks, cleanup on drag end, and explicit placement mode.
   Do not encode credentials, object addresses or executable selectors in drag data.
2. Reuse notebook Add-rail insertion anchors and durable block IDs. A single
   eligibility/placement resolver supports pointer drops and the touch/keyboard
   action. Do not intercept text editing, native file upload or notebook block
   reordering; unrelated drags remain untouched.
3. Add a thin server adapter that resolves the browser's revision-scoped object
   ID and capabilities against the current project/connection, then produces
   existing notebook source/create-cell operations. Quoted SQL is generated by
   the warehouse adapter, never by concatenating a client label. The resolved
   environment is explicit; no global execution-environment switch.
4. Cross the existing notebook save barrier before preparing the insertion.
   Feed the proposed operations to `NotebookChangeSet.PrepareChangeSet`, show
   source, connection, name and snapshot policy, then apply that exact normalized
   change set after confirmation. Keep the revision/CAS and recoverable journal.
   A stale anchor or changed connection requires review again, not silent append.
5. Reuse full/sample snapshot policy, row/byte/time budgets and source transfer
   publication. A browser preview is never promoted to a complete dataset.
   No data transfer on drop, previewing the change set, or confirming authoring.
6. Reconcile through the normal mutation projection and SSE. Highlight/reveal
   the newly created block using its durable identity; do not add another block
   store, another save queue or a parallel notebook renderer.

## Delivery and verification

First ship warehouse tables and project files, then supported object sources;
prefix selection and additional transports follow with capability tests.
Test desktop native drag and mobile/keyboard placement, exact insertion order,
new-tab notebook identity, cross-project/environment rejection, expired IDs,
renamed/missing objects, dirty-save failures, cancelled review, stale revisions,
read-only sources and unsupported files. Assert no run/preview/transfer request
or authored-file change before confirmation, and no execution on confirmation.
Finally run each supported source explicitly in disposable storage/warehouse
fixtures and verify typed results and cancellation without replacing good data.

As built, fold this contract into `architecture/notebooks.md` and retire the plan.
